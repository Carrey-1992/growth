AI 模块 3 · Prompt、Skill 与 RAG

原地图第 3 周的地址和锚点仍是本页。先把提示和 Skill 分开，再做一个能打印召回片段的最小 RAG。已完成 0 项
依赖版本会变。下面不锁 LangChain4j 的 beta 版本号。动手前打开教程页，以那一页写的坐标为准。本站没有替你跑过这条 RAG 练习。

1 · 结构化 Prompt

重点：指令、例子、上下文、输入要分开。角色只是收束语气，不是魔法。

是什么

把提示写成别人能执行的说明：具体指令、三五个有差异的例子、用标签把指令和输入隔开、用一两句角色固定判断标准。长材料放前面，问题放后面。这些是 Claude 提示文档里的写法，不是另一套理论和第 1 模块的循环并列。

为什么这样设计

模型不知道你的读者、格式和成功标准。写给一个不了解背景的同事仍觉得清楚，模型才比较有机会跟着做。标签让你能单独改例子或上下文，而不把整段重写乱。

什么时候会出问题

  • 指令和要求的例子互相矛盾。
  • 例子都一个模样，模型只会模仿那一种。
  • 把真正要回答的问题夹在长上下文中间，模型答非所问。

怎么验证过

留空。用同一份材料写一版含糊提示和一版分开的提示，只记录输出差在哪。

必读 Prompt engineering 概览 的 “How to prompt engineer”。这一节写明：清楚程度、例子、XML、角色、思考和提示串联都放在 Prompting best practices，并称那一页是活参考。从概览页的链接进去。

40 分钟
  1. 选一段你真的会让模型做的说明，例如“给这个接口补测试”。
  2. 改成四块：指令、两个不同的例子、上下文、这次的输入。
  3. 删掉所有“尽量优雅”这类不能检查的句子。

验收：另一人只看提示，能说出成功时长什么样。说不出就还不够具体。

2 · Skill，以及它和规则的差别

重点：规则短、每次都在。Skill 长、用到才加载。一次性提示换会话就没了。

是什么

Skill 是一个目录，核心是 SKILL.md：frontmatter 里有 name 和 description，正文是步骤，还可以带脚本和参考文件。加载是分层的：启动时通常只有名称和描述进上下文；请求对上了才读正文；附件再按需读。Claude Code 和 Cursor 都用这套思路。可以用命令显式调用，也可能在相关时自动用上。

为什么这样设计

第 1 模块的规则文件适合短的项目事实。流程一旦变成“先做 A 再做 B 并核对 C”，继续堆进 CLAUDE.md 会又长又总是占窗口。Skill 把这段流程留到用时再读。一次性提示则每次都要重贴。

什么时候会出问题

  • description 没写清“做什么”和“什么时候用”，自动匹配不会发生。
  • Skill 很多时，描述可能被截短。
  • 会话被压缩后，已读过的 Skill 可能只剩开头。重要限制要写在 SKILL.md 前面。
  • 它仍然不是强制配置。必须拦住的操作，回到第 1 模块的权限或 hook。

怎么验证过

留空。写一个很小的 Skill 并确认未触发时正文没有整篇进入上下文。做不到就不要勾。

必读 Claude 文档中 Agent Skills 的说明（从 Claude Code 概览 进入 Skills）：目录结构、description 的作用、渐进加载。Cursor 侧从 Cursor 文档 的规则 / Skills 页对照“何时进入上下文”。

Claude Code 文档

本张用来找 Skills 章节，不是重读第 1 模块的记忆页。

Cursor 文档

对照项目规则和 Skills 的分工。官方若给出行数建议，以你打开的那一页为准，本页不另写一个数字。

40–60 分钟
  1. 把第 1 模块里那 5 条短规则留在规则文件。
  2. 另写一个只有 30 行的 SKILL.md，description 里同时有任务名和你会说的词，正文是三步可检查的流程。
  3. 用一句无关的话试一次，确认它不应触发；再用 description 里的词试一次。

验收：能说出三条边界：一次性提示、规则文件、Skill。各举本页里的一个例子。

3 · RAG 四个环节

重点：切分、向量、召回、重排。先打通一条能看见召回片段的通路。

是什么

材料放不进窗口、又必须按原文回答时，才在调用模型前先检索。离线把文档切成片段、做成向量放进库；在线把问题也做成向量，取出候选，必要时再打分排序，然后把片段放进提示。LangChain4j 的教程把这分成 indexing 和 retrieval。

为什么这样设计

整库塞进提示又贵又挤。切分是为了让相似搜索有合适的粒度。重排是因为第一次召回经常夹着不太相关的片段，打分后再交给模型，能少看一些噪音。Anthropic 在上下文检索的文章里把“材料不长就可以直接放进提示”当作经验，并给过大约 20 万 token 的量级。那是该文的说法，是否适合你的模型要自己看，本页不把它当成你的阈值。

什么时候会出问题

切分太大，搜索变钝、提示变贵；太小，片段丢掉公司和时间。没有与文档无关的万能长度。向量搜索不擅长精确的类名和编号。这些留到下一张细看。

怎么验证过

留空。必须能打印实际注入的片段，而不能只看最终答案。

必读 LangChain4j RAG 教程 里 Easy RAG 或最小示例那一节：加载文档、写入 embedding store、用 retriever 回答。页面上的版本号以你打开时为准。

选读 同一教程里 ReRanking / Advanced RAG 的小节，知道重排是额外一步即可。

50–60 分钟
  1. 语料用本站第 1、2 模块你已经读过的笔记，或两三篇短官方文档。里面要有不看原文就答不出的细节。
  2. 按教程当前写法接通内存向量库。把接口结果里的回答和来源片段都打印出来。教程若使用 Result.sources() 或检索回调，以教程页的方法名为准。
  3. 问两个问题：一个原文里有，一个原文里没有。

验收：笔记里有一次“片段里真有答案”和一次“片段里没有”的原文摘录。没有 sources 输出就不算做完。

4 · 召回错还是生成错

重点：先看注入的片段。片段里没有事实，是召回问题；片段里有而答错，是生成问题。

是什么

四个环节都会失败。切分边界和重叠会影响后两步。过滤太严会漏，太松会把别的主题带进来。重排救不回“根本没进候选”的正确答案。生成阶段仍可能漏用或编造。

为什么这样设计

只看最终答案无法决定该改切分还是改提示。把 sources 打出来，是为了把责任分到检索或生成。

什么时候会出问题

  • 片段只有“营收增长 3%”，没有公司与时间。这是 Anthropic 上下文检索文章里的例子，用来说明切得太碎。
  • 问题里的类名必须精确匹配，纯向量可能漏。该文提到可以再叠加词法检索。最小练习不必上混合检索。
  • 教程里的 maxResults、minScore、切分 token 数都是示例，不是通用默认值。Easy RAG 页若写了默认切分和默认 embedding 模型，以该页为准，不要背旧讲义里的 beta 号。

怎么验证过

留空。至少各记录一条召回失败和一条生成失败。

必读 上一张的教程里你用来打印 sources 的那一段，再加 Contextual Retrieval 里讲切分丢失上下文、以及词法检索作为补充的段落。读不到某一节就在笔记里写“这一节没找到”，不要编一个小节名。

40–50 分钟
  1. 用同一批问题，至少 6 个：措辞和原文差很多的、带精确类名的、文档里没有的。
  2. 每题只记三行：期望中的原文、实际片段、答案对不对。
  3. 把失败分成召回或生成。若片段里没有依据却答得很肯定，根因先记召回。

验收：能拿自己的一条记录讲清分类，而不是背定义。

5 · 回忆题

先答再展开。

  1. 结构化提示至少要分开哪几块？
    参考答案

    指令、例子、上下文、当前输入。角色用来收束语气和标准。长材料放前面、问题放后面。

  2. 一次性提示、规则文件、Skill 有什么差别？
    参考答案

    一次性提示换会话通常要重贴。规则文件短，被应用时进入上下文。Skill 是带描述的流程包，用到才读正文。

  3. RAG 的四个环节？
    参考答案

    切分、向量、召回、重排。重排不能找回没进入候选的片段。

  4. 切得太大或太小会怎样？
    参考答案

    太大则搜索变差、提示变贵。太小则片段缺少必要上下文，例如只有涨幅没有公司与时间。

  5. 怎样区分召回错和生成错？
    参考答案

    看实际注入的片段。片段里没有所需事实是召回错。片段里已有正确事实但模型答错、漏用或编造，是生成错。
