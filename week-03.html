讲义 · 四栏卡片

是什么

结构化 Prompt：官方把 Prompting best practices 当作当前写法的活参考，概览页也指向它。要点是：指令写清楚、写具体（把它当成很能干但缺少你方背景的新员工）；用 3–5 个相关且有差异的例子（few-shot / multishot）来固定格式和语气；用 XML 标签（如 <instructions>、<example>、<context>）把指令、例子、上下文、输入分开；用 system prompt 给一个角色，哪怕一句话也有用。长文档（官方按 20k+ tokens 计）放到提示前面，问题放在后面。来源 ↗来源 ↗

Skill：可复用的、基于文件系统的能力包，把流程、上下文和最佳实践做成「按需加载」的专长，而不是某一次对话里的临时指令。一个 Skill 通常是一个目录，里面有 SKILL.md（YAML frontmatter 的 name / description + 正文），还可以带脚本和参考资料。加载是分阶段的（progressive disclosure）：启动时只把名称和描述放进上下文；匹配到相关请求后才读正文；资源文件再按需读取。Claude Code 与 Cursor 都采用这套 Agent Skills 思路，可以用 /skill-name 显式调用，相关时也可以自动触发。来源 ↗来源 ↗来源 ↗

和第 1 周规则文件的关系：CLAUDE.md、Cursor Rules、AGENTS.md 是持久指令，被应用时会进入上下文（Cursor 官方写的是放到模型上下文开头）。Claude Code 官方建议：同一段说明你老是在聊天里重贴，或 CLAUDE.md 里某段已经从「事实/约定」长成一套流程时，就做成 Skill——Skill 的正文只在用到时才加载，长参考资料在用到之前几乎不占上下文。Cursor 也支持把符合条件的动态规则和斜杠命令迁到 Skills。来源 ↗来源 ↗来源 ↗来源 ↗

RAG：在把问题交给 LLM 之前，先从你自己的数据里找出相关片段并注入提示，用来补模型训练数据里没有的领域知识，降低胡编的概率。LangChain4j 把过程分成离线的 indexing 和在线的 retrieval。本周要抓住的四个环节是：切分（把文档拆成较小的 TextSegment）；向量（用 embedding 模型把片段变成向量，存进 embedding store / 向量库）；召回（把用户问题也做成向量，按相似度取出候选片段）；重排（用打分模型对候选再排序，再注入提示让 LLM 生成）。来源 ↗

为什么这样设计

为什么要结构化 Prompt：模型不会自动知道你的规范、读者和成功标准；写得越具体，输出越接近你要的结果。官方的检验办法是：把提示拿给一个几乎没有背景的同事看，如果人会困惑，模型大概率也会。XML 标签的作用是避免指令、例子和上下文被搅在一起，也方便你单独增删某一段。给角色是为了把语气和判断标准收束到你的场景。来源 ↗

为什么用 Skill 沉淀团队知识，而不是每次贴一大段 Prompt：一次性 Prompt 是会话级指令，换一次对话就要再贴一遍。Skill 写一次，相关时自动加载，还可以组合多个 Skill。按需加载是为了让你能装许多 Skill，却不必把每份长流程都预先塞进上下文——未触发时只占名称和描述。规则文件适合短而稳定的项目约定；流程和可执行步骤更适合放进 Skill。来源 ↗来源 ↗

为什么要切分：知识库大到放不进上下文时，才需要 RAG（Anthropic 该文的经验是：大约不到 20 万 tokens 的材料可以直接放进提示；这是该文的说法，是否适合你的模型和场景要自己验证）。切分是为了让相似度搜索更有效，并减小送进模型的提示体积和费用。过大的整篇文档既不利于检索，也会把提示撑得很贵。来源 ↗来源 ↗

为什么还要重排：初次召回（知识库很大时尤其如此）往往会返回大量相关度不一的片段。重排用专门的打分模型按与查询的相关性再打分，只把最相关的交给生成模型，从而提高回答质量，并减少模型要处理的信息（有助于成本和延迟）。LangChain4j 的 Advanced RAG 里，这一步对应 ReRankingContentAggregator（配合 ScoringModel）。来源 ↗来源 ↗

什么时候会出问题

  • 切分：粒度、切分边界和 overlap 都会影响召回效果，没有与文档无关的万能数字。来源 ↗太大：相似度搜索变差，注入提示的文本更长、更贵。来源 ↗太小：单段缺少必要上下文。Anthropic 的例子是：片段只有「该公司营收较上季增长 3%」，却没有公司和时间，既难被问「ACME Corp 2023 年 Q2 营收增长」的查询召回，召回了也对生成帮助有限。来源 ↗
  • 向量：向量检索擅长语义相近，但容易漏掉需要精确字面匹配的标识符或术语；该文指出可叠加 BM25 这类词法检索。本周最小实验先把向量检索做通即可，不必一上来上混合检索。来源 ↗
  • 召回：该出现的片段没有进入候选（切分丢了上下文时尤其常见），或不相关片段进来干扰生成。过滤过严（例如 minScore 太高、maxResults 太小）会漏，过松会引入噪音。教程里 Naive RAG 示例用过 maxResults(5) 和 minScore(0.75)，那是示例参数，不是通用默认值。来源 ↗来源 ↗
  • 重排：不做重排时，相关度参差的片段会一并送进模型。做了重排会多一步运行时开销，候选数量和最终 top-K 需要按场景权衡；若正确答案根本没进入初召回的候选，重排也救不回来。来源 ↗来源 ↗
  • 生成仍然可能错：四个环节之后，模型还可能答错、漏用或编造。判断「召回错还是生成错」的办法：把实际注入的片段打印出来。LangChain4j 可把 AI Service 的返回值包成 Result<String>，用 result.sources() 看召回内容（流式则用 onRetrieved）。片段里没有答题所需事实，是召回错；片段里已有正确事实，模型却答错或编造，是生成错。来源 ↗
  • Skill / 规则不被遵守或根本没加载：description 要同时写清「做什么」和「什么时候用」，并尽量包含用户会说的词，否则可能不触发。Skill 很多时，名称列表里的描述可能被截短，自动匹配会变差。会话压缩后，已调用 Skill 可能只保留开头，重要指示应放在 SKILL.md 靠前位置。规则文件仍然只是上下文不是强制配置（见第 1 周）；Cursor 官方建议单条规则控制在 500 行以内，过长就拆开。来源 ↗来源 ↗来源 ↗来源 ↗

周末动手实验（半天）

  1. 新建一个小的 Maven 项目。按 LangChain4j RAG 教程 ↗ 做最小通路：教程的 Easy RAG 需要 dev.langchain4j:langchain4j-easy-rag，当前文档页上的版本是 1.24.0-beta34（beta 版本会变，动手前再对一下该页）。ChatModel 的坐标按你实际要用的提供方，在官方文档里核对后再写（这里不罗列其它提供方坐标，未核实，以官方文档为准）。
  2. 准备一组技术文档作为语料。建议直接用本站第 1–2 周讲义（把 week-01.html / week-02.html 另存为文本，或复制四栏正文），也可以另存两三篇你正在读的官方短文。文档里要有一些「必须靠原文才能答对」的细节，例如某条规则的具体限制、某个类名。
  3. 按教程加载文档、切分、向量化并写入内存向量库：FileSystemDocumentLoader.loadDocuments(...)，InMemoryEmbeddingStore，EmbeddingStoreIngestor.ingest(documents, embeddingStore)。Easy RAG 在文档里写明的默认切分是：每段不超过 300 tokens，重叠 30 tokens；默认 embedding 模型是 bge-small-en-v1.5（进程内 ONNX）。来源 ↗
  4. 用 EmbeddingStoreContentRetriever 和 AiServices 接上问答。把接口返回值做成 Result<String>，每次回答都打印 result.content() 和 result.sources()（召回片段全文，不要只看最终答案）。来源 ↗
  5. 至少准备 6–8 个问题，其中要包含：原文里有明确答案的；措辞和原文差别较大的；需要精确标识/类名的；以及你故意问一篇文档里没有的内容。逐题记下：召回了哪些片段、答案对不对。
  6. 记录召回失败：凡是正确答案不在 sources() 里，或召回的是另一主题的片段，都单独记一条（问题、你期望命中的原文、实际召回的片段、你猜失败发生在切分、向量还是召回过滤）。
  7. 区分「召回错」和「生成错」：对照上一步的片段。片段中没有依据却答得很定 → 召回错（若模型还编了细节，是在错误上下文上又生成错了，根因仍先算召回）。片段中已有依据但答错、漏用或编造 → 生成错。再补 1–2 个「片段里其实有答案」的问题，专门观察生成是否用对材料。
  8. 可选：不要 Easy RAG 的默认切分，改用 DocumentSplitters.recursive(...) 自己指定大小和 overlap（教程示例是 1000 tokens、重叠 200，那只是示例）。换一两组参数重新入库，用同一批问题对比召回命中率，看太大/太小是否出现上面说的症状。来源 ↗

回忆题

  1. RAG 的四个环节各自可能在哪里失败？
    参考答案

    切分：粒度、边界或 overlap 不当，片段丢掉必要上下文，后面怎么搜都难。向量：语义相近的能搜到，但需要精确字面匹配的标识或术语可能漏掉。召回：该出现的片段没进入候选，或不相关片段进来了；过滤过严会漏、过松会引入噪音。重排：初次召回的候选里如果根本没有正确答案，重排救不回来；不做重排时，相关度参差的片段会一并送给模型。

  2. 切分粒度太大/太小分别有什么后果？
    参考答案

    太大：相似度搜索变差，注入提示的文本更长、更贵。太小：单段缺少必要上下文，例如只写「营收增长 3%」却没有公司和时间，既难以被正确查询召回，召回了也对生成帮助有限。切分边界和 overlap 同样会影响效果，没有与文档无关的万能数字。

  3. 重排（rerank）解决的是什么问题？
    参考答案

    初次召回（知识库很大时尤其如此）往往会返回大量相关度不一的片段。重排用打分模型按与查询的相关性再排序，只把最相关的交给生成模型，从而提高回答质量，并减少模型要处理的信息（有助于成本和延迟）。它多一步运行时开销；如果正确答案没有进入初召回的候选，重排也无法把它变出来。

  4. Skill 和一次性 Prompt 的区别是什么？
    参考答案

    一次性 Prompt 是某次对话里的指令，换会话通常要再贴一遍。Skill 是可复用的、基于文件系统的能力包（通常是带 SKILL.md 的目录，还可以附脚本和参考资料），按需加载：未触发时只占用名称和描述，匹配到相关请求后才读入正文。适合沉淀团队流程和领域知识。它和第 1 周的规则文件也不同：CLAUDE.md / Cursor Rules / AGENTS.md 是持久指令，被应用时进入上下文；流程从约定里长出来以后，更适合做成 Skill，避免每次都把长说明预先塞进上下文。

  5. 怎么判断一次回答是“召回错”还是“生成错”？
    参考答案

    把实际注入提示的召回片段打印出来（LangChain4j 可用 Result.sources()，流式可用 onRetrieved），不要只看最终答案。如果片段里根本没有答题所需的事实，是召回错；如果片段里已经有正确事实，模型却答错、漏用或编造，是生成错。
