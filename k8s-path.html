近期路线：K8s 命令与排障

必修大约 13 小时。单次 30–60 分钟，一个周末若集中做四类故障，合计约 3–4 小时。不按日历推进，也不要求在入职前全部做完。
这是 K8s 入职准备里建议先走的一条线，页面不写雇主、部门技术栈或内网地址。AI 模块在 另一页，两条线都不必先做完另一条。你已经有 Docker/K8s 和学习集群，也做过一次 Pod 自动扩展的简单实验。本路线不重装环境，也不把自动扩展的全部机制算成已经掌握。Java 基础不重复。

节做什么建议时长
1只读资料、确认上下文、健康基线、第一份镜像故障证据90–110 分钟，可拆成两段

4Service 不通，分层看标签、端口、EndpointSlice、就绪60 分钟

实验边界

  • 只新建命名空间 lab-troubleshoot。清理只删除这个命名空间里本节创建的对象。确认里面没有别的东西之后，才可以删除这个命名空间本身。不要删除已有的其他命名空间。
  • 先看 current-context。家里学习集群 learn 的上下文通常是 kind-learn。对不上就停，不要换到别的集群继续。
  • 不改节点，不改系统 containerd 或 cgroup，不使用 sudo，不安装新集群，不申请 cluster-admin，不把宿主机内存打满。
  • 资源数字从你当时看到的 Allocatable 算出来。下面不写死超过学习节点的 CPU 或内存。
  • 本页命令没有在你的集群上运行。预期现象来自官方文档对状态和事件的说明，以及 2026-11-21 读到的页面。你的终端原文才是证据。
  • 实验环境页记录过节点一度不能直接拉外网镜像（2026-11-12 的笔记，不是今天的测量）。若拉取失败，先读 Events 里的原因，再决定是 tag 不存在，还是仓库不可达。

第 1 节 · 现在就能做

这一节不要先写 Job，也不要先开 Java 工程。产出是一份故障证据记录：健康对象长什么样，镜像拉不下来时日志和 Events 分别有什么。

1. 只读这几页

必读 调试 Pod 的“诊断问题”“调试 Pod”，以及下面三小节：Pod 停滞在 Pending、Pod 停滞在 Waiting、Pod 处于 Crashing。读的时候只回答：这三种情况分别先看什么，哪一种根本还没有应用日志。

必读 kubectl 快速参考 的“kubectl 上下文和配置”“查看和查找资源”“与运行中的 Pod 进行交互”。

选读 kubectl logs 选项表里的 -p/--previous、-c/--container、--since、--since-time、--tail、--timestamps、-l/--selector。这一节先认识它们，崩溃实验再用。

阅读问题：Pending、镜像拉取失败、进程崩溃，是不是都该先看应用日志？先自己答，再展开。

对照

不是。调试 Pod 页把 Pending 归为还没调度到节点，Waiting 的常见原因之一是拉镜像失败，此时容器还没按应用的方式跑起来。进程已经启动又退出，才更有条件谈容器日志。所以三类故障不能都用 kubectl logs 开头。

2. 最少命令：你在哪个集群、哪个命名空间

kubectl config current-context
kubectl config get-contexts
kubectl cluster-info
kubectl get ns

上下文是 kubeconfig 里“当前在和哪个集群、哪个用户说话”。命名空间是名字的隔离范围。-n 只影响这一条命令；kubectl config set-context --current --namespace=lab-troubleshoot 会改当前上下文的默认命名空间。本路线每次都显式写 -n lab-troubleshoot，避免把默认命名空间改到别处后忘记改回来。

验收：笔记第一行写下 current-context 的原文。不是学习集群就停止。

3. 健康基线

先看集群里已经在跑的镜像，避免假定某个公共 tag 一定拉得下来。

kubectl get pods -A --field-selector=status.phase=Running -o jsonpath="{range .items[*]}{.metadata.namespace}{' '}{.metadata.name}{' '}{range .spec.containers[*]}{.image}{' '}{end}{'\n'}{end}"

从输出里选一个你确认属于学习用途、且对应 Pod 为 Running 的镜像，下面记作 KNOWN_IMAGE。不要把密钥或私有仓库地址抄进公开笔记。

kubectl create namespace lab-troubleshoot
kubectl -n lab-troubleshoot create deployment ok --image=KNOWN_IMAGE --replicas=1
kubectl -n lab-troubleshoot get deploy,rs,pods -o wide
kubectl -n lab-troubleshoot get pods -l app=ok
kubectl -n lab-troubleshoot describe deploy ok
kubectl -n lab-troubleshoot describe pod -l app=ok

create deployment 会带上标签 app=ok。这是这条命令的约定，不是所有 Pod 都有这个标签。选择器 -l app=ok 只匹配带这个标签的对象。

若这个镜像也拉不下来：不要改 containerd。记录 Events 原文。需要一个真能跑的基线时，用实验环境页里已有的做法，在主机上 docker pull 再 kind load docker-image --name learn，前提是上下文确实是这个 kind 集群。加载后仍失败，就停在证据记录，不要为了“变绿”去删系统 Pod。

预期（未在你的集群验证）：调度成功时，describe 的 Events 里会出现调度和拉取相关记录，Pod 最终可以是 Running。容器只有一个时，logs 不需要 -c。若镜像没有持续输出，logs 为空也正常，把“命令成功但没有行”写进记录。

验收：记录里有 Pod 名、所在节点、镜像、Ready、重启次数。这四项缺一个，第 2 节先不要做。

4. 第一份故障：镜像 tag 不存在

用一个肯定不存在的 tag，这样即使仓库可达也会失败。它和“仓库根本连不上”的事件原文不同。两种都先抄 Events，不要凭状态名猜。

kubectl -n lab-troubleshoot create deployment pull-bad --image=nginx:this-tag-does-not-exist-lab --replicas=1
kubectl -n lab-troubleshoot get pods -l app=pull-bad
kubectl -n lab-troubleshoot describe pod -l app=pull-bad
kubectl -n lab-troubleshoot logs -l app=pull-bad --tail=50 --timestamps

调试 Pod 页的“Pod 停滞在 Waiting”写了：Pod 已调度到节点，但还不能在节点上运行，最常见的原因之一是拉取镜像失败，要核对镜像名、镜像是否真的在仓库、本机能否拉取。官方描述的是原因类别，不是你这次的原文。

这时应用日志通常还没有。 logs 失败或提示容器尚未启动，是符合这一阶段的，把命令的退出原文保存下来。不要为了得到日志去 delete pod 或重启节点。

多容器时必须加 -c 容器名。这个错误示例只有一个容器，所以先不要加。容器名在 describe 的 Containers 下面。

kubectl exec 只在容器已经起来、并且你的身份允许时才有意义。镜像没拉下来时，exec 进不去。这不是权限系统坏了。

是什么

ImagePullBackOff / ErrImagePull 表示 kubelet 在拉镜像，并且会按退避再试。对象已经有 Pod，但容器没有进入可以执行应用的状态。

为什么这样设计

镜像身份错了就不应启动进程。事件记在 API 里，所以 describe 能看到，而不依赖应用自己打日志。

什么时候会出问题

tag 写错、仓库不可达、私有仓库没有拉取凭据，表面都可以是 Waiting。凭据问题不要把 Secret 内容贴出来，只记事件里的原因类别。

怎么验证过

留空。把你自己的 describe Events 和 logs 命令结果贴进笔记后再写结论。

本节验收：健康基线和 pull-bad 各有一份。pull-bad 的结论写的是“先看 Events，应用日志缺失是预期”，而不是“日志命令坏了”。

恢复与清理（只动本节对象）

kubectl -n lab-troubleshoot delete deployment pull-bad ok
kubectl get ns lab-troubleshoot

命名空间先留着，后面几节还用。只有整条路线做完、并且 kubectl -n lab-troubleshoot get all 里只剩你创建的残留时，才 kubectl delete namespace lab-troubleshoot。

第 2 节 · 进程崩溃，看 current 和 previous

用已经证明能拉下来的 KNOWN_IMAGE。若这个镜像没有 shell，就不要写 sh -c。nginx 官方镜像可以用错误的配置参数让主进程退出，且仍然只有这一个镜像。

kubectl -n lab-troubleshoot create deployment crash --image=KNOWN_IMAGE --replicas=1 -- nginx -c /no/such-lab.conf
kubectl -n lab-troubleshoot get pods -l app=crash
kubectl -n lab-troubleshoot describe pod -l app=crash
kubectl -n lab-troubleshoot logs -l app=crash --tail=30 --timestamps
kubectl -n lab-troubleshoot logs -l app=crash --previous --tail=30 --timestamps

--previous 的官方说明是：打印容器前一个实例的日志，如果存在的话。第一次还没有退出过，这个参数会失败。等 describe 里出现重启或 Last State 之后再试。没有 previous 是结果，不是命令写错。它也不会把更早的第三份日志找回来。

调试 Pod 页把“Crashing 或不健康”指向容器已经调度之后的进一步调试。describe 里看 State、Last State、Exit Code、Restart Count。不要一上来删掉 Pod，否则前一个实例的日志可能跟着没了。

多容器练习（仍用 KNOWN_IMAGE，避免再拉一个新镜像）：

kubectl -n lab-troubleshoot apply -f - <<'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: two
  labels:
    app: two
spec:
  containers:
  - name: web
    image: KNOWN_IMAGE
  - name: side
    image: KNOWN_IMAGE
    command: ["nginx", "-g", "daemon off;", "-c", "/no/such-lab.conf"]
EOF
kubectl -n lab-troubleshoot logs two -c side --tail=20 --timestamps
kubectl -n lab-troubleshoot logs two --all-containers --prefix --tail=20

把文件里的 KNOWN_IMAGE 换成你的镜像。示例里的 nginx -c 只适用于带 nginx 命令的镜像。参数不被该镜像接受时，把 API 或事件原文记下来，删掉这个 Pod，不要改镜像入口去凑日志。-c 用来指定容器；不指定时，多容器 Pod 的 logs 需要你明确容器或使用 --all-containers。

--since=5m 只保留相对时间窗内的行，--since-time 用 RFC3339，二者只能用一个。--tail 限制行数。排障时先用短 tail 加时间戳，把事件时间和日志时间对齐，再放大窗口。Java 应用若日志里有请求 ID，用同一时间窗去对栈和下游配置；本练习的 nginx 没有请求 ID，不要编一个。

验收：笔记里有一次“还没有 previous”和一次“有 Last State 之后的 previous 或仍然没有”的原文，以及退出码。说不出退出码就还没看 describe。

清理：kubectl -n lab-troubleshoot delete deployment crash pod/two --ignore-not-found

和镜像故障的差别

镜像故障停在拉取，应用进程没开始，logs 常常没有内容。崩溃是进程起来过并退出，logs 和 Last State 才是主要证据。两者都可以叫 BackOff，但证据不在同一处。

第 3 节 · Pending 与 FailedScheduling

request 是调度时预留的数量。节点的 Allocatable 不够，Pod 保持 Pending，调度器写 FailedScheduling。这个 Pod 不会在节点上运行，因此不会把宿主机内存吃光。不要改成“先调度上去再拼命分配”。

kubectl get nodes -o custom-columns=NAME:.metadata.name,CPU:.status.allocatable.cpu,MEM:.status.allocatable.memory
kubectl describe nodes

在 Allocatable 的 memory 上加一截，使请求大于每一个节点的可分配内存。例如你看到的是 4000Mi 左右，请求就写成比它更大的值，并且只放在 requests，不要同时写一个会让容器启动的巨大 limits。若你看不懂单位，停下来读资源页的“内存资源单位”，不要猜一个 100Gi。

kubectl -n lab-troubleshoot apply -f - <<'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: too-big
spec:
  containers:
  - name: pause
    image: KNOWN_IMAGE
    resources:
      requests:
        memory: REPLACE_WITH_MORE_THAN_ALLOCATABLE
EOF
kubectl -n lab-troubleshoot get pod too-big
kubectl -n lab-troubleshoot describe pod too-big

资源页“问题诊断”里的“我的 Pod 处于悬决状态且事件信息显示 FailedScheduling”给了一个文档示例：0/42 nodes available: insufficient cpu。那是文档里的例子，不是你的集群。你要抄的是自己 describe 里的 Events。内存不够时，同一节说消息会类似资源不足。节点名、数字以你的输出为准。

Pending 时不要看应用日志，也不要 delete 再创建来“刷新”。事件已经说明它为什么没被调度。

是什么

Pending 且 Events 为 FailedScheduling：调度器没有找到能满足请求的节点。

为什么这样设计

用请求而不是瞬时用量做调度，是为了在启动前留出位置。实际用量低于请求时，别的 Pod 仍可能因请求总和被挡住。

什么时候会出问题

请求大于所有节点的 Allocatable，或节点有你没有容忍的污点，或端口冲突。文档同一节还写了 hostPort 和污点。本练习只做“请求过大”这一种，避免去改节点污点。

怎么验证过

留空。贴上你的 Allocatable 数字和 FailedScheduling 那一行。

验收：能指出请求值来自哪一次 get nodes，以及为什么这个 Pod 不会压垮宿主机。

清理：kubectl -n lab-troubleshoot delete pod too-big --ignore-not-found

阅读：为 Pod 和容器管理资源 的“请求和限制”“带资源请求的 Pod 如何调度”，以及上面的 FailedScheduling 小节。调试 Pod 的“Pod 停滞在 Pending”。

第 4 节 · Service 访问不通

分层，不要第一步就重启 Pod。顺序：Service 在不在，选择器和 Pod 标签是否一致，端口是否指向容器端口，EndpointSlice 里有没有地址，Pod 是否就绪。

kubectl -n lab-troubleshoot apply -f - <<'EOF'
apiVersion: apps/v1
kind: Deployment
metadata:
  name: svc-demo
spec:
  replicas: 1
  selector:
    matchLabels:
      app: svc-demo
  template:
    metadata:
      labels:
        app: svc-demo
    spec:
      containers:
      - name: web
        image: KNOWN_IMAGE
        ports:
        - name: http
          containerPort: 80
---
apiVersion: v1
kind: Service
metadata:
  name: svc-demo
spec:
  selector:
    app: svc-demo-typo
  ports:
  - name: http
    port: 80
    targetPort: 80
EOF
kubectl -n lab-troubleshoot get pods -l app=svc-demo --show-labels
kubectl -n lab-troubleshoot get svc svc-demo -o wide
kubectl -n lab-troubleshoot get endpointslice -l kubernetes.io/service-name=svc-demo
kubectl -n lab-troubleshoot describe svc svc-demo
kubectl -n lab-troubleshoot describe pod -l app=svc-demo

调试 Service 页的“Service 有 EndpointSlices 吗？”以及调试 Pod 页里的“服务缺少 Endpoints”都要求：用 Service 的选择器去列 Pod，并核对容器端口和 targetPort。选择器写成 svc-demo-typo 时，Pod 可以是 Running，EndpointSlice 仍然没有你的 Pod 地址。这不是应用日志能解释的。

改回正确选择器（只改你创建的 Service）：

kubectl -n lab-troubleshoot patch svc svc-demo --type=merge -p '{"spec":{"selector":{"app":"svc-demo"}}}'
kubectl -n lab-troubleshoot get endpointslice -l kubernetes.io/service-name=svc-demo

就绪实验：在 Deployment 上加一个会失败的就绪探针，观察地址从 EndpointSlice 消失，但 Pod 仍在。探针路径用一个不存在的 URL。把 KNOWN_IMAGE 换掉。若该镜像不监听 80，探针失败会和“端口假设错误”混在一起，先在 describe 里确认容器端口，再加探针。

kubectl -n lab-troubleshoot patch deployment svc-demo --type=json -p '[
  {"op":"add","path":"/spec/template/spec/containers/0/readinessProbe","value":{"httpGet":{"path":"/not-a-real-lab-path","port":80},"periodSeconds":5}}
]'
kubectl -n lab-troubleshoot rollout status deployment/svc-demo --timeout=60s
kubectl -n lab-troubleshoot get pods -l app=svc-demo
kubectl -n lab-troubleshoot describe pod -l app=svc-demo
kubectl -n lab-troubleshoot get endpointslice -l kubernetes.io/service-name=svc-demo

就绪失败会让 Pod 不进入 Service 的可用地址。存活探针失败才会重启容器。这一节只动就绪，避免把“未就绪”和“被杀掉”混成一件事。Pod 生命周期页的“就绪态探针”和“存活态探针”是这两句的阅读位置。

从集群外 curl 不是这一节的验收。很多镜像里没有 curl。验收看的是 EndpointSlice 的地址列表和 describe 里的 Ready。若你已有带 shell 的调试镜像并且拉得下来，可以再做 DNS；做不到就只做下面的只读检查，不要为了 nslookup 去改 kube-system。

kubectl -n kube-system get svc kube-dns

阅读：调试 Service 的“Service 是否存在？”“Service 是否可通过 DNS 名字访问？”“Service 有 EndpointSlices 吗？”“Pod 工作正常吗？”。概念补充：EndpointSlice 开头对“一组网络端点”的定义。

验收：笔记里有三次 EndpointSlice 观察：选择器写错、选择器改对、就绪探针失败。每次都写地址有没有、Pod Ready 是什么。没有这三行不算做完。

清理本节：kubectl -n lab-troubleshoot delete deployment svc-demo svc svc-demo --ignore-not-found

为什么不先删 Pod

选择器错误时 Pod 是好的，删掉只会触发重建，EndpointSlice 仍然对不上。证据在 Service 和 EndpointSlice，不在应用日志。

第 5 节 · 生命周期和 Deployment

把前四节对上术语，而不是再造四个新故障。

  • Pod 阶段、容器的 Waiting / Running / Terminated：Pod 的生命周期 的“Pod 阶段”“容器状态”。镜像拉取失败多半停在 Waiting。崩溃后 Last State 是 Terminated。
  • Deployment 用模板和选择器维持副本。Deployments 的“选择算符”“更新 Deployment”“Deployment 状态”（进行中、完成、失败）。
  • 回滚读同一页的“回滚 Deployment”“检查 Deployment 上线历史”“回滚到之前的修订版本”。

在仍然存在的 ok 上做一次可逆更新。若第 1 节已经删了它，用 KNOWN_IMAGE 再建一个同名 Deployment，不要动别的命名空间。

kubectl -n lab-troubleshoot rollout status deployment/ok --timeout=30s
kubectl -n lab-troubleshoot rollout history deployment/ok
kubectl -n lab-troubleshoot set image deployment/ok *=nginx:this-tag-does-not-exist-lab
kubectl -n lab-troubleshoot rollout status deployment/ok --timeout=20s
kubectl -n lab-troubleshoot describe deploy ok
kubectl -n lab-troubleshoot rollout undo deployment/ok
kubectl -n lab-troubleshoot rollout status deployment/ok --timeout=60s

rollout status 会停在新的 ReplicaSet 还没就绪的时候。这是状态，不是 kubectl 卡死。undo 只回退这个 Deployment 的模板。预期：错误 tag 的新 Pod 再次出现拉取失败，undo 之后回到你记下的上一个修订。修订号以 history 的输出为准，本页不写死一个数字。

验收：history 里能看出修订增加，undo 之后 Running 的 Pod 镜像回到 KNOWN_IMAGE。做不到就不要开始第 8 节。

是什么

Deployment 保存 Pod 模板和修订。滚动更新时新旧 ReplicaSet 会同时存在一会儿。

为什么这样设计

声明的是目标，控制器去靠近它。所以你改镜像之后，旧 Pod 不会永远留着，但失败的新 Pod 也不会被悄悄算成成功。

什么时候会出问题

新镜像拉不下来时，Deployment 可以停在“进行中”或最终失败，旧副本是否还在取决于最大不可用等策略。先看 status 和两个 ReplicaSet，而不是删掉所有 Pod。

怎么验证过

留空。贴 rollout history 和 undo 之后的镜像名。

第 6 节 · DNS、探针、配置

Service 的集群 DNS 名字一般是 服务名.命名空间.svc.cluster.local。阅读位置用你已经打开过的调试 Service 页“Service 是否可通过 DNS 名字访问？”，再读 DNS 与 Service 里说明这条名字如何组成的段落。这一节不要求你在集群里改 CoreDNS。

探针再读生命周期页“容器探针”下的启动、存活、就绪三小节。就绪影响进不进 EndpointSlice；存活失败会重启容器；启动探针用来给慢启动留时间，避免存活探针过早杀掉它。第 4 节已经见过就绪失败。这里只要求你能把三句话写全，不必再造一个会重启的探针。

配置：ConfigMap 开头，读它如何用环境变量或卷进入 Pod。练习只放一行无密文的配置。

kubectl -n lab-troubleshoot create configmap lab-note --from-literal=owner=lab
kubectl -n lab-troubleshoot get configmap lab-note -o yaml

不要把密码、令牌或内网地址放进 ConfigMap。真密文用 Secret，而且不要 -o yaml 后贴到公开处。

和 Java 进程的关系：应用读到的配置来自环境变量、文件或它自己的配置搜索路径。排障时把“Pod 启动时间、ConfigMap 资源版本、日志里的配置路径”按时间排开。配置改了但进程没重启，看到的仍是旧值。本练习不要求你部署 Spring Boot。

验收：用自己的话写清三行：DNS 名字由什么拼成；就绪和存活各影响什么；ConfigMap 改了之后进程为什么可能还在用旧值。

清理：kubectl -n lab-troubleshoot delete configmap lab-note --ignore-not-found

第 7 节 · request 与 limit

request 参与调度（第 3 节）。limit 是运行时的上限。CPU limit 用节流，内存超过 limit 时容器可能被杀掉。资源页“我的容器被终止了”给了一个文档示例：Last State Reason 为 OOMKilled，Exit Code 为 137。那是文档样本，里面的节点和 IP 不要抄。它说明的是“超过内存限制可以被杀掉”，不是“任何 137 都一定是内存限制”，节点压力等别的路径也会杀容器。看到 137 仍要读 Last State 和 Events。

本路线不做把宿主机打满的实验，也不要求你故意制造 OOM。若你希望看一次容器级限制：仅当第 3 节看到的可分配内存至少有 1Gi，并且你接受这个容器自己被杀时，才给一个很小的内存 limit（例如 32Mi）并跑一个会分配内存的进程。不确定就跳过，验收改为复述文档示例和你的第 3 节 Pending 证据。不要把 limit 设成接近整台机器。

阅读：同一资源页的“请求和限制”和“我的容器被终止了”。

是什么

request 是调度账单，limit 是运行上限。

为什么这样设计

分开之后，可以超额承诺 limit，同时仍用 request 保证最低位置。所以“机器看起来还有空闲”和“Pod 仍 Pending”可以同时成立。

什么时候会出问题

只设了很小的内存 limit，进程会被 OOMKilled。只设了很大的 request，Pod 永远 Pending。不要把这两种都叫成“资源不够”而不看事件。

怎么验证过

留空。至少写下你的 Allocatable，以及你有没有做那个可选的小 limit。没做就写“未做”。

官方客户端列表：客户端库。Java 库仓库是 kubernetes-client/java。版本和 execute() 的写法以你打开 README 的那一天为准。本页不锁版本，也没有编译过。

第 9 节 · Job

阅读 Job 里说明“运行到完成”的开头，以及失败后如何重试的段落。用 KNOWN_IMAGE。若镜像忽略参数并一直运行，这个对象就不是完成型任务，记下现象并删掉，不要为了凑 Complete 去改集群默认。

kubectl -n lab-troubleshoot create job hello --image=KNOWN_IMAGE -- nginx -v
kubectl -n lab-troubleshoot get job,pods -l job-name=hello
kubectl -n lab-troubleshoot logs job/hello --tail=20 --timestamps
kubectl -n lab-troubleshoot describe job hello

nginx -v 对官方 nginx 镜像通常会打印版本并退出。若你的 KNOWN_IMAGE 不是 nginx，换一个它支持的“打印后退出”的参数；没有这样的参数就跳过 Job 的运行，只读文档。不要拉取一堆新镜像试错。

验收：能说出 Job 和 Deployment 的差别：一个要到达完成，一个要维持副本。日志用 logs job/hello 或具体 Pod 都可以，前提是容器真的启动了。

清理：kubectl -n lab-troubleshoot delete job hello --ignore-not-found

第 10 节 · RBAC 与配额

阅读 RBAC 里 Role 与 RoleBinding 的部分：Role 只在一个命名空间生效。不要创建 ClusterRoleBinding。

kubectl -n lab-troubleshoot create serviceaccount reader
kubectl -n lab-troubleshoot create role pod-reader --verb=get,list --resource=pods
kubectl -n lab-troubleshoot create rolebinding reader --role=pod-reader --serviceaccount=lab-troubleshoot:reader
kubectl auth can-i list pods -n lab-troubleshoot --as=system:serviceaccount:lab-troubleshoot:reader
kubectl auth can-i delete pods -n lab-troubleshoot --as=system:serviceaccount:lab-troubleshoot:reader

预期来自 RBAC 的规则本身，而不是一次已运行的记录：list 应为 yes，delete 应为 no。若 --as 被拒绝，说明当前身份不能模拟，把原文记下并停止，不要去改集群的模拟权限。

配额读 资源配额 开头：配额约束的是命名空间里的请求总和。数字必须小于你在第 3 节看到的 Allocatable。若可分配内存小于 512Mi，跳过创建配额，在笔记里写原因。

做法：把内存请求配额设成 Allocatable 的大约两成（你自己算，写成 Mi）。然后提交一个 requests 略大于这份配额的 Pod。它应在准入阶段被拒绝，而不是 Pending 到节点上。拒绝原文里会提到配额。这和 FailedScheduling 不是同一种失败。

验收：笔记里分得清 403、配额拒绝、FailedScheduling 三句话各对应哪条命令。

清理：删除你创建的 role、rolebinding、serviceaccount、resourcequota 和那只超额 Pod。不要删除 kube-system 里的任何 Role。

第 11 节 · 状态同步

控制器反复比较 spec 和 status。第 5 节里，你把镜像改成不存在的 tag 之后，Deployment 不会假装已经成功；undo 是在改期望状态，而不是去容器里手工改文件。阅读仍用 模块 1 里已经写过的控制器说明，以及 Deployment 页的“Deployment 状态”。

Java 侧若要监听变化，用客户端的 watch 或 informer，而不是每秒 list 全命名空间。模块 1 有这段背景。本路线只要求你能说出：list 一次加上从某个 resourceVersion 开始的 watch，版本过旧时要重新 list。不要在这一节写一个新的监听程序，除非第 8 节的只读列出已经成功。

验收：用 pull-bad 或 rollout 的那次失败，讲清“期望镜像”和“容器并没有跑起来”如何同时出现在 describe 里。
