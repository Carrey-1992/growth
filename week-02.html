AI 模块 2 · MCP 架构与最小调用

原地图第 2 周的地址和锚点仍是本页。先读架构，再做一个只暴露一个 Tool 的本地练习。已完成 0 项
协议版本以 2026-11-21 打开的规范 2026-07-28 为准。更早的 2025-06-18 架构页仍把 MCP 写成有状态会话和 initialize 握手。旧教程和现行规范不一致时，以你正在读的那一版标题为准，不要混用。

1 · Host、Client、Server

重点：Host 是应用。每个 Server 配一个 Client，一对一。2026-07-28 起，规范把协议写成无状态。

是什么

MCP 管的是应用和外部工具、数据之间怎么交换上下文，不规定你用哪家模型。Host 是 Claude Code、编辑器这类应用。Host 为每个 Server 建一个 Client。Client 只连这一个 Server。Server 提供工具、资源和提示模板，可以在本机，也可以在远处。

为什么这样设计

一个 Server 出问题，不应拖垮其他连接。完整对话留在 Host，Server 只拿到完成这一次请求所需的信息，也看不到兄弟 Server。2026-07-28 架构页写明：协议是无状态的，每个请求自己带上协议版本和能力。

什么时候会出问题

  • 按旧教程先发 initialize，而对方已是 2026-07-28：要以 server/discover 和请求上的 _meta 为准。传输总览的 Backward Compatibility 写了如何探测旧服务器。
  • Server 不支持你带上的协议版本时，会返回 UnsupportedProtocolVersionError 并给出它支持的版本。这是版本不一致，不是业务工具写错。
  • 通知是尽力送达。重连之后不能假设刚才的变更通知一定到了。

怎么验证过

留空。读完后用自己的话画三方关系。没有画之前不要勾成已验证。

必读 Architecture（2026-07-28） 的 Core Components（Host / Clients / Servers）和 Capability Negotiation。看 server/discover 和 _meta.io.modelcontextprotocol/clientCapabilities。

选读 2025-06-18 Architecture 的开头一句（stateful session）和 Capability Negotiation 里的 initialize。只为看出新旧差别。

架构页勾选

读完 Core Components 和 Capability Negotiation 再点 ✓。链接是 2026-07-28 规范，不是旧的 learn 概览。

40–50 分钟
  1. 只读上面两节。在纸上画 Host、两个 Client、两个 Server。
  2. 写下：谁创建 Client，一个 Client 连几个 Server，请求上要自带什么。
  3. 用一句话写下你看到的无状态，和 2025-06-18 那句 stateful 的差别。写不出就说明还没对上页，不要靠记忆。

验收：能不看图讲清一对一，并能指出“无状态”写在 2026-07-28 架构页的哪一节。

2 · Tools、Resources、Prompts

重点：Tool 会执行。Resource 提供数据。Prompt 是可复用模板。模型靠名字和描述决定叫不叫。

是什么

Tools 是模型可以调用的函数，例如按城市查用户。Resources 是给模型看的数据，例如表结构或文件，本身不执行副作用。Prompts 是可复用的交互模板。发现用各自的 list，执行工具用 tools/call。

为什么这样设计

把“做事”“读数据”“固定一种问法”分开，Host 才能分别做权限和展示。工具集可以变，所以先 list 再 call，并可以订阅列表变化。变更通知仍是尽力送达。

什么时候会出问题

  • 该做成 Resource 的只读说明被做成 Tool，模型会为了“看一眼”去执行。
  • name、description、inputSchema 含糊，模型不调用或填错参数。这和第 1 模块的“工具要难以用错”是同一件事。
  • 从 2026-07-28 起，Sampling、Logging、Roots 标为弃用。新代码不要再依赖它们。Logging 的迁移是：stdio 写 stderr，观测走 OpenTelemetry。见 Deprecated Features 表。

怎么验证过

留空。等最小练习里真正看到 tools/list 的返回，再把字段抄进笔记。

必读 Tools 里工具如何被列出和调用的说明；Resources 开头对资源的定义；Prompts 开头。

选读 Deprecated Features 表中 Sampling、Logging、Roots 三行的 Deprecated in 和 Migration path。

40 分钟
  1. 为“按城市查 CSV”各写一句话：哪个是 Tool，哪个如果只是表头说明就应该是 Resource。
  2. 给 Tool 起一个具体名字，写两句 description：一句含糊，一句写清参数和返回。
  3. 说出 list 和 call 的先后，以及通知丢了以后客户端还应做什么。

验收：能举一个会误用 Tool 的例子，并说出弃用的是 Sampling、Logging、Roots，而不是 Tools 本身。

3 · stdio 与 Streamable HTTP

重点：消息含义相同，传输只负责怎么送。stdio 的 stdout 只能写协议消息。

是什么

传输总览写明：语义在所有传输上一样。stdio 是客户端拉起的子进程，一行一条 JSON-RPC，经 stdin/stdout 传递。Streamable HTTP 是向同一个 MCP 端点发 HTTP POST，响应该是 JSON 或这次请求的 SSE。旧的 HTTP+SSE 传输已在更早的修订里标为弃用，迁移方向是 Streamable HTTP。

为什么这样设计

本地一个进程用 stdio，没有为了协议再开网络端口。远程、要鉴权时用 HTTP。规范允许用标准 HTTP 鉴权；具体令牌怎么拿，读授权页，不要在笔记里写真实 token。

什么时候会出问题

  • stdio 页写明：Server 不得往 stdout 写任何不是合法 MCP 消息的内容。日志可以写 stderr。往 stdout 打普通日志会把消息流弄坏。
  • 客户端不应把 stderr 上的任何输出都当成失败。
  • 取消方式不同：stdio 发 notifications/cancelled；Streamable HTTP 关掉这次响应流。不要混用。

怎么验证过

留空。练习若失败，先看是不是日志写到了 stdout，再猜别的。

必读 Transports 总览 开头两段和 Backward Compatibility；stdio 页列出 stdin/stdout/stderr 的那一组要求。

选读 Streamable HTTP 对 POST 和 SSE 的定义。远程服务再读。

40 分钟
  1. 抄下 stdio 页里关于 stdout 和 stderr 的两条必须/可以。用自己的话各写一句。
  2. 决定你的最小练习用 stdio。写出为什么现在不用 HTTP。
  3. 列出一个你会误写到 stdout 的日志例子，并改成 stderr。

验收：能说明两种传输不改变 Tool 的含义，以及 stdout 污染会怎样。

4 · 最小调用：一个 Tool

重点：先读 SDK 仓库里当前的 README 和示例。本页不写死类名和版本号。

2026-11-21 没有在这里编译 Java SDK，也没有对 Maven Central 上的版本号做核对。仓库更新后，示例类名会变。以你打开 modelcontextprotocol/java-sdk 时 README 和 examples 的文字为准。

是什么

最小 Server：stdio 传输，一个 Tool users_find_by_city，参数只有必填字符串 city，返回匹配行。数据用一份本地 CSV。日志只写 stderr。

为什么这样设计

一个 Tool 就够看出 list 和 call。先不要做 Resources 以外的第二套框架，也不要接远程鉴权。可选的第二个原语才是 Resource：只提供表头说明，体会它和 Tool 的差别。

什么时候会出问题

  • 照着旧博客写 initialize 和已经对不上的依赖坐标。
  • description 写成“查询用户”，模型不知道要传城市。
  • 把 CSV 路径或令牌写进公开笔记。本练习只用本地假数据。

怎么验证过

留空。只有当你自己看到 tools/list 和一次调用结果后才填写。本页没有示例输出可抄。

Java SDK

打开 README，确认当前构建方式和示例入口。不要把本站旧讲义里的类名当成现行 API。

规范入口

2026-07-28 规范首页。用来确认你读的修订号。旧链接 /docs/getting-started/intro 不再当作本模块的依据。

50–60 分钟
  1. 读 README 里和 stdio server 示例对应的那一节，把依赖坐标抄到自己的工程，不要抄到本站。
  2. 准备 users.csv，三五行即可，含 city 列。
  3. 按示例实现一个 Tool。用 Inspector 或宿主的 MCP 配置看 tools/list。Inspector 文档：MCP Inspector 的介绍页，确认你用的是哪一个客户端再往下点。
  4. 问一次“某城市有哪些用户”。然后把 description 改含糊，再问一次，只记录有没有调用、参数对不对。

验收：笔记里有 list 的工具名和参数，以及 description 改写前后的差别。没有跑起来就不要勾实验完成。

5 · 回忆题

先答再展开。版本题要能说出你读的是哪一版规范。

  1. Host、Client、Server 的数量关系？
    参考答案

    Host 是应用，为每个 Server 创建一个 Client。一个 Client 只连一个 Server。一个 Host 可以连多个 Server。

  2. 2026-07-28 里“无状态”指什么？
    参考答案

    架构页写每个请求自带协议版本和能力，服务器不靠上一请求留下的会话状态。能力发现用 server/discover。旧修订使用 initialize 会话，不要混为一谈。

  3. Tools、Resources、Prompts 怎么区分？
    参考答案

    Tool 执行操作；Resource 提供上下文数据；Prompt 是可复用的交互模板。

  4. stdio 为什么不能往 stdout 打日志？
    参考答案

    stdout 只承载协议消息。普通日志会破坏分帧。规范允许把日志写到 stderr。

  5. 哪些能力在 2026-07-28 标成弃用？
    参考答案

    Deprecated Features 表里包括 Sampling、Logging、Roots，以及 Dynamic Client Registration。HTTP+SSE 在更早修订已弃用。Tools 本身没有被标成弃用。
