🚀 CI/CD：GitLab CI（推送式）→ Argo CD（GitOps）

2026-11 由 Ubuntu管家 安装、开发大师兄 设计配置 · 本页按群里记录整理，未在机器上复核 · 建在 kind 集群 learn 之上

环境清单

组件装了什么位置 / 要点
GitLab CEgitlab/gitlab-ce:19.5.4-ce.0，Docker Compose 跑在主机上（不在 kind 里），端口 8929（网页）、2224（SSH）~/k8s-lab/ci/docker-compose.yml；省内存配置写在 GITLAB_OMNIBUS_CONFIG：Puma 单进程（worker_processes = 0）、Sidekiq 并发 10、关掉自带监控、自带 Registry 和 KAS。数据在 /srv/gitlab/{config,logs,data}。实测占内存约 2.9GiB。
GitLab Runnergitlab/gitlab-runner:v19.5.3，实例级 Runner，Docker executor配置在 /srv/gitlab-runner/config；job 容器挂主机的 /var/run/docker.sock，网络模式 kind（job 能直接访问 learn-control-plane:6443）；拉镜像策略 if-not-present。
本地镜像仓库registry:2，容器名 kind-registry，只监听主机 127.0.0.1:5001，并接入 kind 网络主机推 localhost:5001/...；节点 containerd 用 certs.d/localhost:5001/hosts.toml 把这个名字映射到 http://kind-registry:5000。镜像名在两边都写 localhost:5001/...。
项目GitLab 私有项目 root/demo-app（从 ~/k8s-lab 用 git subtree split --prefix demo-app 切出来推上去）CI/CD 变量 KUBECONFIG：File 类型、Protected，内容是 kind get kubeconfig --name learn --internal（server 是 https://learn-control-plane:6443，管理员权限）。
流水线三个阶段 test → build → deploytest：maven:3.9-eclipse-temurin-21 跑 mvn test（走阿里云 Maven 镜像，缓存 .m2）；build：docker:cli 用主机 Docker 构建并推 localhost:5001/demo-app:$CI_COMMIT_SHORT_SHA；deploy：alpine/k8s 执行 kubectl set image + rollout status --timeout=180s，只在 main 上跑。

流水线核心（demo-app/.gitlab-ci.yml）

stages: [test, build, deploy]
variables:
  IMAGE: localhost:5001/demo-app:$CI_COMMIT_SHORT_SHA
test:
  stage: test
  image: maven:3.9-eclipse-temurin-21
  cache: { key: m2, paths: [.m2/repository] }
  script: [mvn -s settings.xml -B -Dmaven.repo.local=.m2/repository test]
build:
  stage: build
  image: docker:cli
  script: [docker build -t $IMAGE ., docker push $IMAGE]
deploy:
  stage: deploy
  image: alpine/k8s:1.37.0
  environment: learn
  script:
    - kubectl -n demo set image deployment/demo-app demo-app=$IMAGE
    - kubectl -n demo rollout status deployment/demo-app --timeout=180s
  only: [main]

安装步骤（按记录还原）

# 1. GitLab + Runner
sudo mkdir -p /srv/gitlab/{config,logs,data} /srv/gitlab-runner/config
cd ~/k8s-lab/ci && docker compose pull      # GitLab 镜像约 6GB
# 查出真实版本后把 latest 固定成 19.5.4-ce.0 / v19.5.3
docker compose up -d && docker logs -f gitlab   # 约 2–5 分钟后网页可用

# 2. 本地仓库接入 kind
docker run -d --restart=always -p 127.0.0.1:5001:5000 --name kind-registry registry:2
docker network connect kind kind-registry
docker exec learn-control-plane grep -n config_path /etc/containerd/config.toml   # 原来没有
# 备份后在 [plugins."io.containerd.grpc.v1.cri".registry] 下加 config_path = "/etc/containerd/certs.d"
docker exec learn-control-plane mkdir -p /etc/containerd/certs.d/localhost:5001
printf '[host."http://kind-registry:5000"]\n' | docker exec -i learn-control-plane tee /etc/containerd/certs.d/localhost:5001/hosts.toml
docker exec learn-control-plane systemctl restart containerd
docker push localhost:5001/demo-app:v1 && docker exec learn-control-plane crictl pull localhost:5001/demo-app:v1

# 3. 注册 Runner（glrt- 令牌只留在本机）
docker exec -it gitlab-runner gitlab-runner register --non-interactive \
  --url http://<主机IP>:8929 --token <glrt-令牌> \
  --executor docker --docker-image alpine:3.20 \
  --docker-volumes /var/run/docker.sock:/var/run/docker.sock \
  --docker-network-mode kind --docker-pull-policy if-not-present

# 4. 建项目、加 KUBECONFIG 变量（File、Protected），推代码触发流水线
kind get kubeconfig --name learn --internal
git subtree split --prefix demo-app -b demo-app-only
git push <gitlab 仓库地址> demo-app-only:main

踩过的坑

  1. 节点 containerd 没配 config_path，certs.d 目录不生效：先备份 config.toml，补上配置后只重启节点里的 containerd，节点保持 Ready、Pod 都在 Running。
  2. gitlab-rails runner 报 cannot load such file：docker cp 进去的脚本权限是 600，容器里的 git 用户读不了，chmod 644 解决。
  3. 镜像标签里的 version 是 24.04，那是底层 Ubuntu 的版本；GitLab 真实版本要看容器里的 /opt/gitlab/version-manifest.txt。
  4. 原计划要改 Docker 的 NO_PROXY 并重启 Docker，查过后取消了：代理只配在 Docker 守护进程上（只影响主机拉镜像），没有注入容器，节点 containerd 也没有代理变量，所以不用重启，集群没断。

现状和要注意的

  • 配置漂移：集群里跑的是 localhost:5001/demo-app:4353b205，但 manifests/40-demo-app.yaml 里还写着 demo-app:v1。哪天重新 apply 这个清单，就会退回旧镜像。这正是下一阶段 GitOps 要解决的问题。
  • 源码有两份：~/k8s-lab/demo-app 和 GitLab 仓库。以后以 GitLab 为准，克隆下来改。
  • 凭据：root 初始密码文件 24 小时后会自动删除，过期后用 docker exec -it gitlab gitlab-rake "gitlab:password:reset[root]" 在本机终端重置；安装时生成的 root API 令牌（30 天过期）和 Runner 令牌放在 Ubuntu 本机的 ~/.config/gitlab-lab/（权限 600），不用的令牌在 GitLab 里撤销。这些都不写进笔记。
  • 内存：GitLab 约 2.9GiB，Runner 和仓库各约 20MiB，整机还剩约 21GiB 可用。

值得深挖的 6 个点（每张卡读完点 ✓）

Runner 怎么领活、job 在哪跑

先读，理解整体

是什么：GitLab 本身不跑 job。Runner 主动向 GitLab 轮询要任务，领到后按 executor 执行；Docker executor 会为每个 job 起一个新容器（镜像由 job 的 image 指定），跑完就删。GitLab Runner：Docker executor ↗ .gitlab-ci.yml 关键字参考 ↗

为什么这样设计：调度（GitLab）和执行（Runner）分开，Runner 可以装在任意能连到 GitLab 的机器上，横向加机器就能加并发；每个 job 一个干净容器，环境可重复。

什么时候会出问题：job 之间不共享文件系统，要靠 cache（加速，如 .m2）或 artifacts（传产物）；镜像拉取策略 if-not-present 会用到本地旧镜像，标签不变时可能拿到旧内容。

怎么验证：跑一次流水线时 docker ps 看 Runner 临时起的 job 容器；在 job 日志开头找 executor 和镜像信息；把 cache key 改掉再跑，对比 test 用时。

build 为什么挂 docker.sock，代价是什么

对应流水线 build 阶段

是什么：job 容器里没有 Docker 守护进程，挂进主机的 /var/run/docker.sock 后，docker build/push 实际由主机的 Docker 执行，所以 localhost:5001 指主机本身。另一种做法是 Docker-in-Docker。在 GitLab CI 里构建 Docker 镜像（socket 挂载与 DinD） ↗

为什么这样设计：简单、快，能直接复用主机的镜像缓存，不用 privileged 容器。

什么时候会出问题：能访问 docker.sock 基本等于拿到主机 root：任何能改 .gitlab-ci.yml 的人都能控制整台机器。学习环境可以接受，多人共用的 Runner 不能这样配；同时多个 job 共享主机 Docker，镜像和容器名可能冲突。

怎么验证：在一个测试分支的 job 里执行 docker ps，看能不能看到主机上的 gitlab、kind 节点容器，理解风险（看完就删分支）。思考题：换成 Kaniko 或 BuildKit 无守护进程构建，要改哪些地方？

节点怎么拉到 localhost:5001 的镜像

对应 kind 本地仓库

是什么：节点里的 localhost 是节点容器自己，不是主机。containerd 读 certs.d/localhost:5001/hosts.toml，把对 localhost:5001 的拉取转到 kind 网络里的 kind-registry:5000。kind 本地镜像仓库 ↗ containerd 仓库配置 hosts.toml ↗

为什么这样设计：镜像名在主机、CI 和集群里保持一致，只在节点这一层做地址映射，不用改清单。

什么时候会出问题：containerd 没配 config_path 时 certs.d 不生效（这次就踩了）；kind 重建集群后要重新配，应写进 kind-config.yaml 的 containerdConfigPatches；仓库是 HTTP 无认证，只适合本机。

怎么验证：docker exec learn-control-plane crictl pull localhost:5001/demo-app:v1；临时把 hosts.toml 改名后再拉，看报什么错，再改回来。

推送式部署：set image + rollout status

对应模块1（Deployment 控制器）

是什么：deploy job 拿着 kubeconfig 直接调用 API Server 改 Deployment 的镜像，Deployment 控制器随后滚动更新；rollout status 一直等到新版本就绪，超时就让 job 失败。kubectl rollout status ↗

为什么这样设计：上手最简单，CI 一条龙，失败能直接在流水线里看到。

什么时候会出问题：集群的真实状态只存在集群里，和 Git 里的清单会漂移（这次 40-demo-app.yaml 还是 v1）；CI 要拿集群的写权限；回滚要靠重跑旧流水线或 kubectl rollout undo。

怎么验证：改一行代码 push，看新 Pod 名和镜像标签；故意把健康检查路径改错 push，看 deploy 是否在 180 秒后失败，再用 kubectl rollout undo 回滚。

流水线的集群凭据和最小权限

练习题，模块1 之后做

是什么：现在 KUBECONFIG 变量是管理员权限，File 类型会在 job 里落成一个临时文件，Protected 表示只在受保护分支（main）上可用。GitLab CI/CD 变量（含 File 类型、Protected） ↗ K8s RBAC 授权 ↗

为什么这样设计：File 类型让 kubectl 直接读；Protected 防止任意分支拿到生产凭据。

什么时候会出问题：管理员凭据一旦泄漏，整个集群都能被改；任何能推 main 的人都能用到它。

怎么验证：练习：建一个 ServiceAccount，只给 demo 命名空间里 deployments 的 get/patch 和 pods 的 list/watch 权限，生成它的 kubeconfig 换掉变量，确认 deploy 仍然成功，而 kubectl get nodes 会被拒绝（403）。

下一步：GitOps 和 Argo CD

阶段二，做完 c1–c5 后

是什么：把期望状态放在 Git 里（比如单独的部署清单仓库），Argo CD 在集群里持续比对 Git 和集群，发现不一致就同步回来。CI 只负责测试、出镜像、改清单仓库里的镜像标签，不再直接碰集群。Argo CD 文档 ↗ OpenGitOps 原则 ↗

为什么这样设计：本质还是控制器的调谐循环（和模块1 同一个思路），只是期望状态的来源换成了 Git：可审计、可回滚（revert 一次提交），CI 不需要集群凭据。

什么时候会出问题：多了一个仓库和一个组件要维护；镜像标签的更新要自动化（CI 改清单或用镜像更新工具）；有人手动改集群会被 Argo CD 改回来，要先约定好。

怎么验证：装 Argo CD 后，用 kubectl set image 手动改一次镜像，看 Argo CD 显示 OutOfSync 并自动改回；再在 Git 里 revert 一次，看集群跟着回滚。

建议学习顺序

  1. 先读本页“环境清单”和“第一次流水线”，对照 GitLab 网页上那条流水线的三个 job 日志。
  2. 读 c1、c2、c3，搞清楚一个 job 在哪跑、镜像怎么构建、节点怎么拉到它。
  3. 做 c4 的故障实验（改坏探针、看 deploy 失败、回滚），再给 demo-app 补几个单测（需要 MySQL 的用 H2 或 Testcontainers），让 test 阶段真正有意义。
  4. 学完模块1 后做 c5 的最小权限练习。
  5. 最后做 c6：装 Argo CD，把配置漂移这个问题用 GitOps 解决掉，写成一篇对比文章（推送式 vs 拉取式）。
