🧪 实验环境：家里 Ubuntu 的 kind 集群 learn

2026-11-11 晚至 11-12 凌晨由 Ubuntu管家 搭建 · 本页按它的记录整理，未在机器上复核 · 后面所有模块的实验都在这套环境上做

环境清单

部分搭了什么关键文件 / 要点
集群kind 集群 learn，节点镜像 kindest/node:v1.37.0；装回 metrics-server v0.9.1（带 --kubelet-insecure-tls）和 Headlamp v0.46.0~/k8s-lab/kind-config.yaml：extraPortMappings 把主机 80/443 映射进节点，节点标签 ingress-ready=true。端口映射只能建集群时定，所以删了重建。
镜像节点不能直接拉外网镜像主机先 docker pull，再用 ~/k8s-lab/kind-load.sh（底层 kind load docker-image）导入，清单在 images.txt。
应用demo 命名空间：demo-app（Spring Boot 3.5.7 + Java 21，Actuator + micrometer-prometheus），镜像 demo-app:v1（多阶段 Dockerfile）；mysql:8.4（local-path 卷 2Gi，schema.sql 写入 3 条用户）；redis:7-alpine（访问计数）源码 ~/k8s-lab/demo-app/；账号密码在 Secret 里，由 manifests/ 下脚本生成；接口 /、/visits、/users、/actuator/health、/actuator/prometheus；探针接 Actuator。
Ingressingress-nginx v1.12.1（kind 专用清单）manifests/ingress-nginx-kind.yaml；按域名转发 demo.local、grafana.local、prometheus.local；局域网和 ZeroTier 访问都 200，客户端要改 hosts。
HPAdemo-app CPU requests 100m、limits 500m；HPA（autoscaling/v2）1–5 副本，CPU averageUtilization 50%，即每 Pod 平均 50m压测见下方表格；清单 manifests/60-hpa.yaml、80-loadtest.yaml，记录 ~/k8s-lab/hpa-scaleup.log。
监控helm v4.3.1 装 kube-prometheus-stack 93.2.0（release kps，monitoring 命名空间），Prometheus v3.16.0 + Grafana 13.3.1，关了 Alertmanagervalues 在 monitoring/kps-values.yaml；关了 etcd、controller-manager、scheduler、kube-proxy 的抓取（kind 里抓不到）；*NilUsesHelmValues: false 让 Prometheus 抓所有 ServiceMonitor；保留 2 天、最多 4GB、PVC 5Gi。manifests/70-servicemonitor.yaml 按 app: demo-app 选 Service 的 http 端口，15 秒抓一次 /actuator/prometheus；Grafana 管理员密码在 Secret kps-grafana 里（不要写进笔记）。

搭建命令（按 ~/k8s-lab 文件还原的等价命令）

xargs -a images.txt -n1 docker pull        # 主机经代理拉
./kind-load.sh $(cat images.txt)
kubectl apply -f manifests/metrics-server-kind.yaml -f manifests/headlamp.yaml
kubectl apply -f manifests/ingress-nginx-kind.yaml
cd demo-app && docker build -t demo-app:v1 . && ../kind-load.sh demo-app:v1 && cd ..
kubectl apply -f manifests/00-namespace.yaml && manifests/create-secret.sh
kubectl apply -f manifests/10-config.yaml -f manifests/20-mysql.yaml -f manifests/30-redis.yaml   -f manifests/40-demo-app.yaml -f manifests/50-ingress.yaml -f manifests/60-hpa.yaml
helm install kps monitoring/kube-prometheus-stack-93.2.0.tgz -n monitoring --create-namespace -f monitoring/kps-values.yaml
kubectl apply -f manifests/70-servicemonitor.yaml
curl -H 'Host: demo.local' http://<主机IP>/users

踩过的坑

  1. 节点连不上 registry.k8s.io 等仓库，Pod 卡在 ImagePullBackOff：主机经代理 docker pull 再导入节点。
  2. Docker 29 默认用 containerd 镜像库、存多平台镜像，kind load docker-image 失败：改成 docker save --platform linux/amd64 后 kind load image-archive（见 kind-load.sh）。
  3. 导入后 Pod 仍去外网拉：kubelet 留着之前的拉取记录，停 kubelet、清 /var/lib/kubelet/image_manager/pulled|pulling 后重启。
  4. ServiceMonitor 默认不被抓：kps 只认 release: kps 标签，用 *NilUsesHelmValues: false 放开。
  5. 搭建任务并发跑两遍覆盖了源文件：pom.xml、schema.sql 从运行中的 jar 取回，Dockerfile 重写并验证构建。

值得深挖的 6 个点（每张卡读完点 ✓）

kind 怎么用容器模拟节点

模块1 之前，热身

是什么：每个“节点”其实是一个 Docker 容器，里面跑 systemd、containerd 和 kubelet，kubeadm 在里面拉起控制平面。kind 设计：用容器当节点 ↗

为什么这样设计：本机就能起多节点集群，秒级重建，适合学原理和 CI；代价是网络、存储都隔了一层容器。

什么时候会出问题：端口映射只能建集群时定（所以这次重建）；节点拉不到外网镜像，要 kind load；节点容器重启后数据卷要靠 local-path 是否落在主机上。kind 里配 Ingress（端口映射） ↗

怎么验证：docker ps 看到 learn-control-plane 容器；docker exec -it learn-control-plane crictl ps 看节点里的容器。

Ingress Controller 怎么把 Ingress 变成 nginx 配置

对应模块1（控制器、list-watch）

是什么：Ingress 只是一份声明，自己不转发流量；Controller 通过 list-watch 监听 Ingress、Service、Endpoints 等对象，生成 nginx 配置并加载。Ingress 概念 ↗ ingress-nginx 文档 ↗

为什么这样设计：和 Deployment 控制器一样是“声明式 + 调谐循环”，换实现（nginx、Envoy 等）不用改 Ingress 对象。

什么时候会出问题：ingress-nginx 官方已宣布停止维护，新项目应看 Gateway API。K8s 博客：ingress-nginx 停止维护 ↗ Gateway API ↗ 另外 Ingress 表达力有限，很多功能靠注解，不同 Controller 不通用。

怎么验证：kubectl -n ingress-nginx exec deploy/ingress-nginx-controller -- cat /etc/nginx/nginx.conf | grep demo.local；改一下 Ingress 再看日志里的 reload。

HPA 的计算公式和稳定窗口

对应模块2（requests 与调度）

是什么：期望副本数 = ceil(当前副本数 × 当前指标 / 目标指标)。CPU 利用率是相对 requests 算的，这里 requests 是 100m、目标 50%，即每副本约 50m。HPA 自动扩缩容（算法、稳定窗口） ↗

为什么这样设计：缩容默认有 300 秒稳定窗口，取窗口内最大建议值，防止负载抖动导致副本来回震荡。

什么时候会出问题：没设 requests 就算不出利用率；limits 太紧会被 CPU 限流，看起来像“扩了也不快”；扩容还受节点资源限制，Pod 会 Pending。

怎么验证：对照 hpa-scaleup.log：用 45 秒那次的 386% 套公式算出应扩到几个，再查 HPA 默认 scaleUp 策略，解释为什么实际先扩到 4、15 秒后才到 5（讲解题，自己推完再对照文档）；kubectl describe hpa 看事件。

metrics-server 与 Prometheus 两条指标链路

对应模块2、3

是什么：metrics-server 从各节点 kubelet 采集 CPU/内存，提供给资源指标 API（metrics.k8s.io），只存最近值，供 HPA 和 kubectl top 用。metrics-server ↗ Prometheus 按抓取配置拉 /metrics 类接口，存时序数据，用于监控和告警。

为什么这样设计：前者轻量、只为自动伸缩服务；后者全面、能查历史。想按 QPS 等业务指标扩缩容，要再接一个 custom/external metrics 适配器。

什么时候会出问题：--kubelet-insecure-tls 只适合学习环境；metrics-server 挂了 HPA 会拿不到指标而停止调整。

怎么验证：kubectl get --raw /apis/metrics.k8s.io/v1beta1/namespaces/demo/pods 对比 Prometheus 里同一 Pod 的 CPU。

ServiceMonitor 与 Operator 的 CRD 机制

模块4 之后，扩展阅读

是什么：ServiceMonitor 是 Prometheus Operator 定义的自定义资源（CRD）；Operator 监听它，自动生成 Prometheus 的抓取配置。Prometheus Operator ↗

为什么这样设计：把“运维知识”写进控制器：你声明想抓谁，Operator 负责改配置、重载，又是调谐循环。

什么时候会出问题：kube-prometheus-stack 默认只认带 release: kps 标签的 ServiceMonitor，这次就踩了这个坑，改 serviceMonitorSelectorNilUsesHelmValues: false 解决。

怎么验证：Prometheus 页面 Status → Targets 看 demo-app；kubectl get servicemonitor -A 和 kubectl get prometheus -n monitoring -o yaml 对 selector。

探针接 Actuator 的讲究

对应模块1

是什么：就绪探针失败只会把 Pod 摘出 Service，存活探针失败会重启容器。存活、就绪、启动探针 ↗

为什么这样设计：分开是为了区分“暂时不能接流量”和“已经坏了要重启”。

什么时候会出问题：存活探针如果也检查 MySQL/Redis，依赖一抖，所有 Pod 会被一起重启，造成雪崩；Spring Boot 的 liveness/readiness 分组可避免。

怎么验证：停掉 Redis，看 demo-app 是变成未就绪还是被重启。

建议学习顺序

  1. 先读本页“环境清单”，确认每样东西在哪。
  2. 学模块1 时，配合深挖 1、2、6：用这套集群做 list-watch 实验，再去看 ingress-nginx 怎么 watch。
  3. 学模块2 时，配合深挖 3、4：用现成的 HPA 压测记录验证公式和 requests 的作用。
  4. 模块3、4 做完后读深挖 5，理解 CRD + Operator，这也是 Kueue 的工作方式。
  5. 以后可以把 ingress-nginx 换成 Gateway API 实现，做一次对比实验，写成一篇文章。
